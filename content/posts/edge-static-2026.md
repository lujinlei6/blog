十年前的争论是「要不要做 SSR」。现在的争论是「**哪一部分在什么时候渲染**」。

这两者不是同一个问题。前者是二选一，后者是一条连续谱。

## 渲染时机的四个位置

```
构建期 ──────────── 部署期 ──────────── 请求期 ──────────── 客户端
 prerender            ISR               SSR              CSR
 最便宜                                                    最灵活
```

| 位置 | 谁付出计算成本 | 内容新鲜度 | 失败模式 |
| --- | --- | --- | --- |
| 构建期预渲染 | 你的 CI | 与代码同步 | 内容变更需重新构建 |
| 增量再生（ISR） | 边缘节点，后台 | 分钟级 | 首个请求可能拿到旧内容 |
| 请求期 SSR | 你的服务器，每次 | 实时 | 服务器挂了就是全站挂 |
| 客户端渲染 | 用户的设备 | 实时 | 首屏空白，SEO 依赖额外手段 |

关键洞察是：**同一个站点通常同时需要好几个位置**。博客的正文属于构建期，评论数属于请求期，搜索结果属于客户端。

## 「静态」的现代含义

预渲染不再意味着「一堆手写的 HTML 文件」。现代框架的预渲染是**真的启动你的应用、跑一遍路由、抓取渲染结果**：

```ts
tanstackStart({
  prerender: {
    enabled: true,
    crawlLinks: true,        // 从入口页出发，跟着链接爬
    autoSubfolderIndex: true, // /posts/x → /posts/x/index.html
    concurrency: 14,
    failOnError: true,
  },
})
```

这意味着你写的是完整的框架代码——loader、server function、类型安全路由全都在——只是最后一步把结果冻结成了 HTML。

`crawlLinks` 解决了预渲染最经典的痛点：**动态路由怎么枚举**。你不需要手动列出所有文章 URL，构建器从首页开始跟着 `<a>` 爬，只要文章列表页链接到了每一篇文章，它们就都会被预渲染。

反过来这也暴露了一个陷阱：**没有被任何页面链接到的动态路由不会被预渲染**。孤儿页面在构建产物里就是缺失的。

## 什么时候预渲染是错的

三种情况：

**1. 内容量级大且更新频繁。** 一万个商品页，每天改价，预渲染会让每次构建跑几十分钟。这时候 ISR 或者请求期渲染更合适。

**2. 页面依赖请求上下文。** 需要读 cookie、判断登录态、按地理位置定制——预渲染的 HTML 对所有访客是同一份。

**3. 构建链本身不稳定。** 预渲染要在构建环境里真实运行应用，任何环境差异（Node 版本、缺失的环境变量、依赖外部 API 而构建环境访问不到）都会让构建失败。

第三条最容易被低估。SSR 出问题时你在运行时能看到日志、能降级；预渲染出问题时你在 CI 里对着一堆堆栈猜。

## 一个诚实的例子

这个博客目前跑的是 **SSR + Nitro**，不是预渲染。

按理说它是预渲染的完美候选：内容是仓库里的 Markdown，只在提交时变化，没有任何请求上下文依赖。预渲染能拿到零运行时成本、可以直接丢 CDN、Lighthouse 分数会更高。

我没这么选的原因是**构建链的确定性**。这个项目刚搭起来，我需要先确认路由、loader、server function、类型系统这一整套东西在 dev 和 build 两种模式下都行为一致，然后再把渲染时机往构建期挪。预渲染会把「运行时问题」变成「构建时问题」，而后者在调试初期更难受。

切换成本是一个配置项，所以这个决定是可逆的——**可逆的决定应该延后做**，先把不可逆的部分（内容模型、路由结构、类型契约）定下来。

## 边缘缓存：被低估的那一层

在 SSR 和预渲染之间还有一个选项经常被忽略：**照常 SSR，但让 CDN 缓存结果**。

```ts
context.response.headers.set('Cache-Control', 'public, max-age=0, must-revalidate')
context.response.headers.set('CDN-Cache-Control', 'max-age=300, stale-while-revalidate=300')
```

这两个 header 是分开的：`Cache-Control` 给浏览器，`CDN-Cache-Control` 给边缘节点。你可以让浏览器每次都校验，同时让 CDN 缓存五分钟并在过期后先用旧内容响应、后台再生成新的。

对内容型站点来说，这个组合的收益接近预渲染，但**保留了完整的运行时能力**——需要的时候依然可以读 cookie、做个性化、返回不同的内容。

代价是你依赖 CDN 的实现。`CDN-Cache-Control` 被主流厂商支持，但具体的 `stale-while-revalidate` 语义各家有差异，上线前要在目标平台实测。

## 怎么选

一个够用的决策顺序：

1. **内容会不会因访客而异？** 不会 → 继续；会 → 请求期渲染 + 边缘缓存
2. **内容变更频率低于部署频率吗？** 是 → 构建期预渲染；否 → 继续
3. **页面数量在千级以下吗？** 是 → 构建期预渲染；否 → ISR
4. **构建环境能可靠地跑通应用吗？** 能 → 预渲染；不确定 → 先 SSR，稳定后再切

大部分博客、文档站、营销页走到第 2 或第 3 步就结束了。

## 别过早优化

最后一点，也是最重要的一点：**这些选择几乎都是可逆的**。

从 SSR 切到预渲染通常是改一个配置项。从预渲染切回 SSR 也是。真正难以更改的是内容模型和路由结构——那些决定一旦写进几十篇文章的 frontmatter 里，迁移成本就是真实的人力。

所以顺序应该是：先把数据契约和路由契约定稳，用最容易调试的渲染方式跑起来，等到有真实的性能数据或者部署成本压力了，再动渲染时机。

在那之前，SSR 是一个完全站得住脚的选择。它不是「还没优化的过渡态」，它是这条谱上一个正当的位置。
